# Try the bounded last-bar engine

The `lastbar` engine is an explicit trial option in the built-in engine catalog. The default remains `exhaustive`. It runs the existing Exhaustive search at its unchanged per-stock-length budget, then spends up to 10,000 additional charged steps on relaxed last-bar rearrangements for that stock length. This is a heuristic, not a proof of optimality or a wall-clock limit. It leaves leftovers unchanged, validates the baseline and every accepted result by exact part reference and fit, and retains Exhaustive's First Fit fallback metadata. No migration is required: saved results record the selected engine id/name through the existing JSON fields.

On a deployment built from this revision, select “Exhaustive + Last-Bar Trial” in a job's Results engine picker, then Optimize or Re-Optimize. Compare it with “Exhaustive” on the same unlocked job. For a non-persisting API preview, use `POST /api/jobs/{id}/pack` with JSON `{"engine":"lastbar"}`; `GET /api/packing/engines` lists the choice. The standalone optimizer and MCP engine selectors also use the catalog. Existing jobs are not recomputed automatically, and publishing a container does not redeploy it.

The previous test-only experiment measured three bars saved across 120 development jobs after Exhaustive with this additional 10k budget. It did not establish held-out quality or an equal-total-budget advantage; see [last-bar-elimination-evaluation.md](last-bar-elimination-evaluation.md). A catalog-to-`MultiBinPacker` regression for repeated seed 36 verifies 98 → 97 bars with exact reference conservation; a zero-budget and invalid-baseline suite verifies no unsafe partial promotion. The pre-existing same-named near-equal part removal defect is fixed by reference-based `Bin.RemoveItem`, covered through the full First Fit and prototype paths. Keep the trial opt-in pending held-out and finite-stock evaluation. The separate bounded replacement prototype remains test-only.
